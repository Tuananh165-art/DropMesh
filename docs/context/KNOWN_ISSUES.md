# Known issues and evidence gaps

- M1 acceptance is incomplete until a two-device LAN test runs with Internet unavailable, matching digests, cancellation, and bounded-resource evidence.
- The checkout tracks the public `Tuananh165-art/DropMesh` repository. Initial hosted run 38344069584 exposed CRLF-sensitive Windows formatting; `.gitattributes` now pins Go sources to LF. Follow-up run 38344545090 passed all native Windows/Linux/macOS tests, all cross-builds, static analysis, Linux race/security/fuzz/benchmark gates.
- Hosted native Windows/Linux/macOS format, vet, and full test suites pass. Linux race, fuzz, benchmark, govulncheck, and Staticcheck v0.8.1 also pass in hosted CI; local Windows race and Linux-container quality runs pass.
- Refreshed `govulncheck@v1.8.0` found no vulnerable symbols or imported packages. It reports only uncalled module-level GO-2026-5932 for `golang.org/x/crypto/openpgp`, with no fixed version; no project package imports OpenPGP. `golang.org/x/net` was upgraded to v0.60.0, removing its five reported module-only HTTP/2 advisories; tidy raised `x/crypto` to v0.57.0 and `x/sys` to v0.48.0.
- Windows/amd64 loopback tests and cross-compilation do not prove physical-LAN behavior. Hosted Linux/macOS suites add native runtime evidence, while Docker Linux-container execution uses overlay storage; none of these runs establishes bare-metal power-loss durability.
- Physical device disk-full/write-fault behavior remains unverified. Injected short writes, data/journal sync failures, and disk-full errors now exercise resume recovery on Windows. An unread QUIC receiver stream also verifies sender backpressure and cancellation cleanup, alongside four incomplete-auth peers timing out and releasing their slots, destination writer failure classification, caller cancellation while the peer is idle, partial-chunk disconnect cleanup, and transfer-cancellation cleanup.
- Staticcheck v0.8.1 and govulncheck v1.8.0 now pass in disposable Linux containers. The Staticcheck workflow's earlier version-qualified `go run -modfile=...` command was invalid; the replacement job-local module downgrade/install/run sequence passed locally. Hosted workflow execution remains unverified.
- Process termination can leave a hidden `.dropmesh-*.partial` file. M1 never reuses partial output.
- Publication requires destination filesystem hard-link support. If rooted hard-link creation fails, transfer fails without overwriting.
- If the receiver publishes but the final completion exchange is lost, sender outcome remains uncertain.
- Invite text is a bearer credential; possession permits one receiver admission before expiry.
- DropMesh is a provisional name with existing product usage. No trademark or domain clearance is claimed.
- Maintainer, security contact, and conduct-enforcement contact are unresolved and block publication.
- M2 is still in progress pending independent protocol/threat review and maintainer signoff of the internal acceptance matrix in `docs/acceptance/M2.md`. Journal records carry commit timestamps so recovery truncation does not refresh the 24-hour idle expiry. Local Windows and hosted Windows/Linux/macOS tests cover process exit around data write/sync, journal record write/sync, and publication cleanup; injected write/sync/disk-full/corruption and malformed duplicate/descending/missing stream cases pass. Linux-container process tests also pass on Docker overlay storage. These tests do not establish power-loss durability.
- Resume mode re-hashes the sender's complete source before and during a run; if source bytes change, the receiver rejects publication and resets committed chunks after whole-file mismatch so a later run can retransmit.
- The output directory may contain `.dropmesh-state/.active.lock` after a completed or deleted transfer. Incomplete state is removed on completion, explicit deletion, or expiry; the lock file itself is retained to avoid lock-file replacement races.
